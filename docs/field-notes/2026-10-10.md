## Critical-path faults fixed

- `osGetCount_recomp` zero-extended `mfc0 Count`. Game timers saw a spurious wrap at 45.8 s (bit 31), produced a huge dt, recursed the animation update until the guest stack overran OSThread's host context pointer at +0x20, and segfaulted in `run_next_thread`. Fixed in librecomp by sign-extending.
- `0x8008C100/0x8008C190/0x8008C280` are osEepromLongRead/LongWrite/Probe, previously stubbed. The save loader never initialised the profile at 0x80113680 and attract mode spun in its random-racer pick. Redirected in `post_recomp_patches.py`; save type is Eep16k.
- Function discovery placed ten real entries inside neighbouring functions (callers `jal` into the middle). Split in `symbols.toml`; the hand-written `func_80044414` and `HAND_ENTRIES` table are gone.
- `0x8008A2F0/0x8008A360/0x8008A3B0` are osViSetMode/osViSwapBuffer/osViBlack and `0x8008C390` is osViSetSpecialFeatures; the old `osViSetMode@0x8008D510` was wrong. Unmapped, VI never reached RT64.
- ultramodern `osViSetMode` did not clear `VI_STATE_BLACK`, so the game's boot `osViBlack(1)` blanked output forever (hstart 0). libultra clears it on mode set.
- SI: the PIF RAM adapter now executes the guest's joybus block (status, read pad; channel 0 only) instead of answering a fixed layout.

## Deck frame pacing, input response and audio (landed 8ce1a44 / runtime 8104ce2)

Binary `build-deck/SWE1Racer` sha256 `a51f88c8…` unchanged from acceptance. Runs `p18-pacing`, `p19-pacing-presents`, `p20-pacing-presents`, `p21-swap-cadence` under `/home/deck/racer-opus-probe/runs/` (mirrored on Pop under the racer-opus `proof/runs/`), each the scripted menu path into a ~80 s Boonta race with accelerate held and 20 steering taps, on headless sway at 60 Hz, not the Deck panel or gamescope.

- Intended rate from the runtime: ultramodern generates VI at a fixed 60 Hz; the game registers `osViSetEvent(0x800D9C10, 3, 1)` (every retrace) and integrates time from `osGetCount`. Its frame loop (`func_8002F750` → `func_80084CC4`) swaps after each completed display list and rotates three framebuffers (0x8063B800, 0x806D2C00, 0x8076A000); it never waits for a retrace. On hardware RDP time throttles it; ultramodern reports SP done immediately and DP done when RT64 has parsed the list, so nothing does here.
- Game-delivered frames (p21, gdb breakpoint on `osViSwapBuffer_recomp`, 30 s mid-race): 7687 swaps, 256/s, interval median 3.67 ms, p99 6.36 ms. Gfx tasks track swaps 1:1 (246/s before, 256/s under, 266/s after the window; 418-449/s in menus), so the breakpoint did not throttle the loop. About three of every four rendered frames are never shown.
- Host-presented frames (MangoHud per-present log, p20 and p21): race 60.0 presents/s, frametime median 16.7-16.8 ms, p1 11.9-12.7, p99 20.7-21.4, max 28.3 ms; 4382 of 4384 race presents (p20) land in one vblank. Menus 58.3/s with load stalls (384-390 ms on entering the track screen, 50 ms frames during boot). MangoHud reports average GPU load ~72 % and CPU ~31 % for the whole run. RT64 presents only on a VI or framebuffer change (`refreshRate` Original, no interpolation), so these are not VI counts.
- Input response (68 key transitions per run, all delivered, 3 runs): SDL host-pad change to guest PIF read median 23-25 ms, p90 ~43 ms, max 48.7 ms. The game reads the pad on a ~20.5 Hz cadence, the same rate it submits audio tasks, not per rendered frame. wtype schedule to SDL is median ~14 ms, but that includes wtype and compositor scheduling. Screen response after the guest read was not measured per frame. Estimated from the cadences above: one ~4 ms game frame plus at most one 16.7 ms present.
- Audio: the game issues audio tasks (type 2, ucode 0x80099450, data 0x800AE5F0) at 20.48/s and sets 48000 Hz. The ROM carries Factor 5 strings, which suggests MusyX microcode. `get_rsp_microcode` answers them with a no-op that reports completion, and `src/audio.cpp` drops samples and reports a constant 2048 frames remaining. Sound needs that RSP microcode recompiled through RSPRecomp (source in the N64Recomp tree, not built on Deck) plus a real SDL sink. The audio capability is absent, not just muted at the sink.

Process findings:
- MangoHud `no_display` never starts `autostart_log`: `update_hud_info` skips the frametime update, and with it the autostart check, unless logging is already active (MangoHud 33c2c7dd `src/overlay.cpp`). Start logging over the control socket (`control=racer-mangohud-%p`, `:logging=1;`). The host SteamOS MangoHud loads in the Arch distrobox via an explicit layer manifest pointing at `/run/host/usr/lib/libMangoHud.so`.
- SIGINT stops the runtime's gfx loop and presents but not the process. Anything that flushes on a present must finish before the harness sends SIGINT.
- The RDRAM framebuffer dump writes PNGs on the render path and is off for timing runs.
- The harness timestamps each game log line on arrival through a FIFO. The game already sets stdout and stderr unbuffered.

## Completion pacing and real audio (game on 8be8cdb, runtime 404d238)

Binary `build-deck/SWE1Racer` sha256 `d4e736e70f5a0f44fc14e125761cb59a86e2f91fdf49057b62374ade93c9fdbe`. Acceptance run `p27-acceptance` under `/home/deck/racer-opus-probe/runs/` (mirrored under the racer-opus `proof/runs/`), the same scripted menu path into an ~80 s Boonta race as p21, headless sway at 60 Hz with MangoHud logging and the SDL `disk` audio driver.

Root causes:
- `0x8008C770` is osViGetCurrentFramebuffer and was stubbed, so the game's triple-buffer guard (`func_80085D4C` spins while the current framebuffer equals the draw target) passed immediately. Mapping it was not enough: ultramodern delivered VI messages only at blocking points, and the spin never blocks. libultra's getter returns through `__osRestoreInt`, which is where hardware takes a pending interrupt, so the runtime getters now dequeue external messages and yield to a higher-priority runnable thread. SP/DP completion ownership is unchanged (ultramodern reports SP done at submit, DP done after RT64 parses the list).
- Audio was silent at four layers. `get_rsp_microcode` returned a no-op; `src/audio.cpp` dropped samples; the AI functions were misidentified (old `osAiSetFrequency@0x800903D0`, `osAiSetNextBuffer@0x80090450` and `osSetIntMask@0x80090170` are synth helpers, the real ones are `0x80088150`, `0x800882B0`, `0x80090500`, plus `osAiGetLength@0x800883E0` and `osAiGetStatus@0x8008ADA0`); and `alSynNew` (named `cache_writeback_800887D0`) and the whole synth library at `0x8008D554`-`0x80090330` and `0x80095B68`-`0x800963CC` were stubbed, so every audio list was empty.
- The microcode is standard libultra `aspMain`, not MusyX (OSTask template at `0x8009A2D0`, text ROM `0x9A050`, 0xE20 bytes, 16-entry dispatch table at DMEM 0x10). RSPRecomp at N64Recomp `81213c1` compiles it from `aspMain.toml`; the output needs SSE4.1 for `_mm_shuffle_epi8`. A task with `data_size == 0` dispatches stale DMEM and crashes with "Unhandled jump target", which is what the stubbed synth produced (p22/p23).
- Un-stubbing exposed misbounded functions: handler entries reached through `lui/addiu` tables (`0x80007710` and others) and the bogus `func_8008E9F4_stub` / `osSetEventMesg_unused_8008EA04` split, now `func_8008E9F0`.

Measured (p27):
- Produced frames: `osViSwapBuffer` 120.1/s over 30 s mid-race (interval median 7.81 ms, p99 13.98, max 16.43), 1200 swaps to each of the three framebuffers; gfx tasks ~120/s inside and outside the gdb window, menus and race alike. p21 was 256/s.
- Presented frames (MangoHud per-present): race 59.99-60.06/s, median 16.66 ms, p99 ~24 ms, max 27.89 ms; menus 59.50/s. Hitches 403.5 ms entering the track screen and 550.6 ms at gdb attach. GPU load 34.7 % (p21 72 %), CPU 25.4 % (31 %).
- Two produced frames per present is the game's own guard with zero RDP time; RDP duration is not modelled.
- Race clock still tracks wall time (00.00 at t060, 09.88 at t070, 1:09.87 to 1:19.88 from t130 to t140). The apparent jump between t070 and t080 in both p21 and p27 is harness timing: those shots fire after the blocking 30 s gdb event (timeline 111015-111819 ms).
- Input: host pad change to guest PIF read median 22.5 ms, max 49.5 ms (unchanged).
- Audio: 148.5 s of real SDL output, guest 22050 Hz resampled to a 48 kHz device. Menu music harmonics, race engine noise with Doppler sweeps, stereo differences in race, mono in menus. No gaps ≥ 10 ms during the race; gaps occur only at menu transitions and race load. Clipping: 41 samples at 81-84 s, 28 at 114 s, a few elsewhere. Artifacts `audio-48000-stereo.wav` and `audio-spectrogram.png`.

Process findings:
- `SDL_AUDIODRIVER=disk` with `SDL_DISKAUDIOFILE` captures the real sink path without touching the host audio server.
- p22-p23 were failed acceptances (crash, then silence) and p24-p26 30 s attract diagnostics on changed binaries; p27 is the only full acceptance on this binary.

Not implemented: RDP timing; pad read at ~20.5 Hz; clipping; SIGINT exit; event ids 3, 8, 14; `thread_queue_remove` defect; pak, rumble and channels 1-3; remaining PI/SI/OS stubs; the `func_80087D70` redirect drops the osJamMesg path; the busy-wait spin holds one core; measured on headless sway, not the panel or gamescope.

## Display aspect: RT64 black-border removal on a 480i mode

The race and menu picture was a 614x904 column (aspect 0.68) centred in the 1280x960 window in every run since p17; only 320x240 screens such as the boot logos looked right. Not a capture artifact: the sway tree in p28 reports the HEADLESS-1 output and the SWE1Racer window both at 1280x960, and grim captures that whole output.

- Intended guest aspect: the game builds its VI mode at `0x80114488` from the libultra `osViModeTable` (`0x800A69C0`) and rewrites it for its render size (`0x8003A000`). The race mode is 480i: VI width 640 as a two-row stride, serrate, xScale 0x200, hStart `0x006C02EC` (640 output pixels, the full active line), vStart `0x23`-`0x1FD` (474 half-lines). On hardware that fills the 4:3 raster.
- RT64 (`../rt64` at 8bd2cf1) estimates that framebuffer as 320x476 (`VI::fbSize`). Its default `presentation.removeBlackBorders = true` makes `VIRenderer::getViewportAndScissor` use the framebuffer size as the display space instead of the 320x240 raster, so a 320x476 framebuffer was shown at 320:476 and pillarboxed. `VI::viewRectangle` is still the full raster at this commit, so with the flag off the VI output fills the 4:3 raster as hardware does. The render context now turns the flag off when it creates the RT64 Application; `aspectRatio` stays `Original`.
- Post-change smoke `p28-aspect` (binary `e138d65b8f6bbc940ec78ad023cf85a26bab3139a648748641dba4ad4c5796f6`, same scripted path as p27, no gdb or MangoHud): picture 1216x904 (aspect 1.345) from t030 to t140. The remaining 32 px side and 34 px top/bottom margins are the game's own framebuffer border (about 8 pixels per side at 320 wide), present in p27 too. Race clock advances 10.00 s per 10 s of wall time (13.13 at t060, 23.13 at t070, 1:13.12, 1:23.11, 1:33.13 at t120-t140). Disk audio is 149.1 s, non-silent, stereo in race.
